# Recommender Feed

A personal reading feed, ranked by LLM agents. Fetches from your sources (RSS or plain
listing pages), triages and summarizes every new item with a cheap model (Haiku), then
ranks the unread queue by **marginal value** with a stronger model (Opus 5.5) — an item's
position accounts for what's ranked above it, so redundant coverage gets discounted.
Your ratings ("critical" → "not worth reading") and notes feed a taste profile the
system regenerates over time. A discovery agent with web search chases your short-term
quests and can propose new permanent sources, which only you can approve. Built
2026-07-26 (first commit) to replace skimming a dozen AI blogs and newsletters by hand
with one queue that already knows what has been covered and what the reader cares about.

## How it works

**Layout.** This repo is the `code/` half of a two-folder project; the `data/` sibling
holds everything private and is never touched by git:

```
recommender-feed/
├── code/   ← this repo (safe to publish; contains no data)
└── data/   ← feed.db, .env, backups/, logs/  (never touched by git)
```

The app resolves the data dir as: `$FEEDAPP_DATA_DIR` if set, else a sibling `../data`
if it exists, else `./data` inside the checkout (gitignored). `make where` prints both paths.

**Two processes, one database.**

- The **API server** (`backend/app/main.py`, FastAPI + SQLite in WAL mode) serves
  `/api/*` and, when `frontend/dist` exists, the built React UI at `/`. It also starts
  manual pipeline runs as a subprocess when you hit ↻ Refresh.
- The **pipeline** (`python -m app.pipeline`, orchestrator in `backend/app/pipeline/run.py`)
  is a plain CLI that launchd runs four times a day. Same code path for scheduled and
  manual runs. Stages, in order: **fetch** (RSS via feedparser; non-RSS listing pages
  via a small Haiku call that picks article links out of the page's anchors) →
  **extract** (trafilatura pulls readable text, content-hash dedup) → **triage** (Haiku:
  summary, topics, 0–10 relevance, source-filter check; ≤60 items per run) →
  **discovery** (Opus + server-side web search, only when a quest is active) →
  extract/triage the discovered items → **ranking** (one Opus call orders the whole
  candidate queue greedily by marginal value, keeping the previous order roughly
  stable) → **profile** (regenerate the taste profile if due) → **interview** (leave the
  reader a question if there is enough fresh signal) → **backup** (always runs last).
  A stage that fails marks the run `partial` and later stages still run with what is
  available. A `pipeline.lock` (flock) stops two runs overlapping; runs that die are
  marked `stale: interrupted` after 60 minutes.

**Desktop app** (added 2026-11-16). `~/Applications/Reading Feed.app` is a small Swift shell
(`desktop/main.swift`): one window with a WKWebView pointed at the API server on
`http://127.0.0.1:8000`. It holds no app logic and does not start the server; the launchd
server agent does that, so the app needs `./install.sh --app` (or `--server`) to have been run.
While the server is down the window shows a waiting page and retries every second. Links to
anything other than the feed UI (articles, sources) open in the default browser. Closing the
window leaves the app running; the dock icon brings it back. Frontend and backend changes need
only a rebuilt frontend and a restarted server; the app is rebuilt only when `desktop/` changes.

**Automatic updates** (added 2026-11-16). `install.sh` sets `core.hooksPath` to `hooks/`, whose
`post-commit` and `post-merge` run `deploy.sh` in the background. It looks at which paths the
commit (or pull) touched: `frontend/` or `backend/` rebuilds the frontend and bounces the
server (`make restart`); `desktop/` or the icon rebuilds `~/Applications/Reading Feed.app` and,
if the app was open, quits it and reopens it in the background. The app compares the served
`index.html` with the one it loaded each time it becomes the active app, and reloads when a
newer frontend build is there. The app's build number (About Reading Feed) is the commit count
it was built from. Nothing is deployed without a commit or pull.

**How it learns.**

- **Ratings** — 4 tiers: critical / worth it / fine / not worth it, plus "Didn't finish"
  (opened but abandoned; treated as evidence the piece failed to hold attention).
  Rate after reading.
- **Notes** — two optional channels on every rating: *raw reading notes* (what you wrote
  for yourself while reading; the profile model infers what held your attention) and
  *feedback to the AI* (the "why?" box; quoted verbatim into the taste profile).
- **Instructions** — the text box on the Instructions page. *Quests* ("find things about
  the recent Hugging Face event") expire after 14 days or when you confirm them done; the
  discovery agent leaves a status note under each quest. *Standing preferences* ("less
  interpretability research") persist.
- **Taste profile** — regenerated by Opus from your ratings + notes (and recent chat)
  every ~8 ratings or 2 weeks; it's what the triage/ranking prompts actually read.
  See it at `/api/profile`.
- **Chat** — a two-way interview with the curator agent (asks one targeted question at a
  time; clear preferences become one-click instruction chips). The pipeline also leaves
  a question proactively when ≥5 ratings have arrived since the agent last spoke.
- **Add a link** — any URL saved on the Feed page is triaged immediately and listed just
  below the ranked items until a ranking run includes it, on its merits among everything else; you can rate it inline if you already read it.

**Without an API key** the app still runs: it fetches RSS sources and shows a
chronological feed; triage/ranking/discovery are skipped.

**LLM standard.** Every model call goes through `backend/app/services/llm.py`, which
prepends the shared preamble from `~/Documents/agent-coding/shared/llm-system-prompt-preamble.md`
to every system prompt, adds the `contact_eli` tool to every call, and runs
`llm_contact.check()` on every response. A `contact_eli` tool call is first followed by one
question (`llm_contact.with_confirm`, added 2026-11-10): did the model mean to reach Eli and stop,
or was it remarking on the task? Haiku was sending routine remarks ("this page has no articles")
several times a day; those now continue to a normal answer and are kept in
`~/Library/Application Support/LLMInbox/unconfirmed.jsonl`. If the model contacts Eli, `LLMContacted` is
raised: the pipeline skips the remaining LLM stages for that run (backup still runs) and
records the message in the run's error field; a chat turn returns HTTP 409 and the UI
shows the message. Nothing is retried. Read and answer with `llm-inbox`
(see `shared/README.md`).

Every call also offers `note_to_eli` (added 2026-11-20), which leaves Eli a message without
stopping anything. `llm.py` runs `llm_contact.with_notes` before the confirm step on every call:
the note is recorded in the LLM inbox (`via: note`, `halts: false`), the tool call is answered
with `NOTE_RESULT_TEXT`, and the model is asked again for its answer (one extra call per note
reply, counted in the run's usage, at most 3 rounds). A note is never the task's answer and
never raises `LLMContacted`. For the prose calls (triage, profile, discovery) any text the model
wrote before the note call is kept in front of the second reply, so an answer given in the same
reply as a note is not lost.

**Costs.** Hard caps per run: ≤60 triage calls (Haiku), 1 ranking call and ≤1 discovery
call (Opus, ≤8 web searches). Roughly $0.50–0.75/run; the per-run estimate is shown
next to the Refresh button and a 30-day daily spend indicator sits in the header
(`/api/usage/daily`, which also counts chat turns).

**Backups** (`backend/app/services/backup.py`) run at the end of every pipeline run: a
verified SQLite snapshot (online-backup API, integrity-checked; a snapshot that fails
is deleted and a live DB that fails `quick_check` never overwrites existing backups), a
plain-JSON export of the precious tables (ratings, items, instructions, conversation,
profiles, sources, proposals), both mirrored to iCloud Drive (`FeedAppBackups/`, or
`FEEDAPP_BACKUP_MIRROR`). Retention: 30 days of dailies plus the earliest backup of each
calendar month forever, locally and on the mirror.

**Converting to a hosted webapp later.** The design is deliberately deployment-portable:

1. The frontend talks to the backend only via `/api` HTTP calls — no local coupling.
2. `make build` + `uvicorn app.main:app` is a single self-contained web process; put it
   behind any host (Fly/Render/VPS) and add an auth layer in front of `/api`.
3. The pipeline is a plain CLI (`python -m app.pipeline`) — swap launchd for cron, a
   container scheduler, or a worker dyno without code changes.
4. Config is env-var based (`ANTHROPIC_API_KEY`, `FEEDAPP_DATA_DIR`).
5. SQLite → Postgres is the only real migration; the schema is vanilla SQL and all
   SQLite-specific code lives in `backend/app/db.py`.

## Common tasks

First-time setup:

```bash
mkdir -p recommender-feed && cd recommender-feed
git clone <this repo> code && mkdir data
cd code && make setup                     # python venv + npm install
cp .env.example ../data/.env && chmod 600 ../data/.env   # then put the real key in it
```

Development (two terminals, open http://localhost:5173):

```bash
make dev-backend
make dev-frontend
```

Single-process (builds the frontend, serves everything at http://localhost:8000):

```bash
make run
```

Build only / run the pipeline (fetch → triage → discovery → rank → profile) manually:

```bash
./build.sh           # or: make build
make pipeline        # or hit ↻ Refresh in the UI
```

Schedule the pipeline (7:30 / 12:30 / 17:30 / 21:30 daily via launchd; missed runs
coalesce on wake) and the always-on server:

```bash
./install.sh             # pipeline only (= make schedule); also retires the old com.elityre.feedapp.* labels
./install.sh --server    # + always-on server (= make install): starts at login, restarts on crash
make restart             # after code changes: rebuild + bounce the server
make status              # show server + pipeline launchd state
make unschedule / make uninstall
```

The app is then permanently at http://localhost:8000.

Desktop app (its own window and dock icon; needs the always-on server):

```bash
./install.sh --app       # pipeline + server + build ~/Applications/Reading Feed.app
make app                 # rebuild the app by hand (a commit touching desktop/ does this itself)
./deploy.sh --all        # rebuild and restart server and app now, whatever changed
tail ~/Library/Logs/recommender-feed-deploy.log   # what the last commits deployed
open ~/Applications/"Reading Feed.app"
make app-test            # load the UI in the app with no window; prints PASS or FAIL
tail -f ~/Library/Logs/recommender-feed-app.log
```

Test without the real trigger (throwaway data dir, no API key, no iCloud; fetches real
RSS, runs extract + backup, checks the run row and the LLM-standard plumbing):

```bash
./test.sh            # or: make test
cd frontend && npm run typecheck
```

Logs and state:

```bash
make logs                                            # tail -f ~/Library/Logs/recommender-feed.log
tail -f ~/Library/Logs/recommender-feed-server.log
make where                                           # repo, data and log paths
make backup                                          # snapshot + export + mirror now
curl -s localhost:8000/api/pipeline/runs?limit=3 | python3 -m json.tool
llm-inbox list                                       # messages the model sent to Eli
```

## Settings that matter

- **Full Disk Access / TCC.** launchd-spawned processes cannot read files under
  `~/Documents`, `~/Desktop`, or `~/Downloads` (TCC privacy protection — they fail with
  "Operation not permitted" and no prompt is shown). If this repo lives there, both
  `make install` and `make schedule` jobs will die on startup. Either keep the checkout
  somewhere unprotected (e.g. `~/Developer/`, with a symlink from `~/Documents` if you
  like), or grant **Full Disk Access** to the Python binary
  (`backend/.venv/bin/python`) in System Settings → Privacy & Security. The current
  install lives under `~/Documents` and runs, so that grant is in place; a new venv
  binary needs it again.
- **iCloud Drive** must be enabled for the off-machine backup mirror; otherwise set
  `FEEDAPP_BACKUP_MIRROR`.
- **Anthropic API key** in `<data dir>/.env`. Without it the feed is chronological only.
- **LLM inbox** notifications (ntfy/email) are configured in
  `~/Library/Application Support/LLMInbox/config.env`, see `shared/README.md`.

## Gotchas learned

- Auto-deploy builds from the working tree, not from a clean checkout of the commit: any
  uncommitted edits sitting in `frontend/`, `backend/` or `desktop/` at commit time go live too.
- The hooks only run if `git config core.hooksPath` says `hooks` (set by `install.sh`; a fresh
  clone does not have it). A failed build is only reported in the deploy log; the old build
  keeps running.
- A pipeline run started from the UI's Refresh button is a child of the server and dies when
  the server restarts. `deploy.sh` therefore waits (up to 20 minutes) for such a run before
  restarting; a hand-run `make restart` does not.

- The desktop app and a browser tab are different origins' worth of storage: drafts typed in
  Chrome (`localhost:8000` or `:5173`) do not appear in the app, and the reverse. Everything
  saved to the server is shared.
- A bare WKWebView has no Edit menu, so Cmd-C/V/Z do nothing in text fields; it drops
  `alert()`/`confirm()` silently; it ignores `target="_blank"` links; and it leaves spell
  check off. `desktop/main.swift` handles each of these, so keep those pieces if it is rewritten.
- `make app-test` passing means the page rendered inside the app's web view against the live
  server. It does not click anything.

- `launchd/*.plist` are templates; `make` substitutes `__REPO__`, `__DATA__` and
  `__LOGS__`. Editing the copy in `~/Library/LaunchAgents` directly is lost on the next
  `make schedule`.
- On 2026-11-07 the launchd labels changed from `com.elityre.feedapp.*` to
  `com.elityre.recommender-feed.*` and logs moved to `~/Library/Logs`. The old pipeline
  label stays loaded (running the old code paths) until `./install.sh` runs; `make
  schedule`/`unschedule` boot out both old and new labels, so rerunning is safe.
- Opus 5: thinking and the reply share `max_tokens`. A truncated structured reply can
  look valid while being garbage, so `llm.py` raises on `stop_reason == "max_tokens"`
  instead of storing it; the interview and ranking calls use a 16k budget for this reason.
- Triage asks Haiku for free prose followed by a fenced JSON block, not a forced JSON output format, and its
  prompt says what `contact_eli` is not for. With the format forced, Haiku used `contact_eli` to talk to the
  reader ("flagging this for your review", "make the call"), and each call stopped the run's triage and
  ranking; the shared confirm step let about half of those through. Measured 2026-11-10/11 on four stored
  inputs, 12 runs each: forced format 5 of 48 called the tool, this setup 0 of 48. A `note_to_reader` field
  in the schema made it much worse (15 of 32). On a request it should refuse (invent quotes to get an author
  fired) it still contacted Eli 11 of 12 times, the same as before. The remaining miss both before and after:
  a refusal that never calls the tool. Now that is a reply with no JSON; the item stays `new`, is retried each
  run, and the full reply is in the pipeline log (`grep "no usable JSON" ~/Library/Logs/recommender-feed.log`).
  Haiku's remarks before the JSON are logged as `[triage] item N remarks:`. Reasoning first also moves scores a
  little (14 items re-triaged: most within 1 point, three dropped 3). Do not reword the last two paragraphs of
  `TRIAGE_SYSTEM` without replaying; full counts are in `shared/README.md`.
- Models moved on 2026-11-16: Haiku 4.5 to Haiku 5.5 (triage, listing pages) and Opus 5 to Opus 5.5 (everything
  else). Three things changed with them. Opus 5.5 defaults to medium effort where Opus 5 ran at high, so
  `llm.py` sends `effort: high` for it (`EFFORT`). Haiku 5.5 thinks by default and thinking shares
  `max_tokens`, so triage went from 2000 to 6000 and listing from 4000 to 8000. And the shared confirm step
  only runs for Haiku 4.5 (`llm_contact.CONFIRM_MODELS`), so on Haiku 5.5 a `contact_eli` call is sent
  straight away and stops the run. Replayed before switching, on a copy of `feed.db`: 10 triage items and 2
  listing pages, no `contact_eli` calls, every reply parsed, scores within 2 points of Haiku 4.5's. The
  objection half (does it still contact Eli about a request it should refuse) was not rerun on Haiku 5.5. The
  Haiku 4.5 measurements in this section describe the old model; if routine `contact_eli` calls start
  stopping runs, replay again before rewording.
- `note_to_eli` went in on 2026-11-20 at night with `api.anthropic.com` blocked, so it has only been run
  against stubbed replies (`./test.sh`, step 1b), never a real model. Not yet known: whether Haiku 5.5 in
  triage uses it to flag articles for the reader (the old `contact_eli` habit; each note costs one more
  call and notifies Eli, but no longer stops the run), whether a real objection still goes to `contact_eli`
  rather than the note tool (which answers "carry on"), and whether the API accepts a discovery turn with
  web-search blocks replayed after a note. The triage prompt's last paragraph names only `contact_eli`; it
  was left as measured. Replay triage before rewording it, and watch the inbox for notes after the first
  real runs.
- Haiku 5.5 caches prompts from about 512 tokens up (Haiku 4.5 needed 4096), so the triage system prefix is
  now cached across a run.
- Many sites (Reuters, paywalls) block non-browser fetchers. A user-saved link must still
  succeed, so it falls back to a slug-derived title and empty content (`''`, so the
  pipeline does not refetch it forever).
- `og:title` is read before trafilatura's metadata guess, which on JS-heavy sites (e.g.
  LessWrong) can return a stray number such as the karma score.
- `index.html` is served with `Cache-Control: no-cache`; without it a stale shell kept
  loading old JS bundles after rebuilds. Hashed assets stay cacheable.
- SQLite connections are opened with `check_same_thread=False` because FastAPI may run a
  sync dependency and its route on different threadpool threads; each request still gets
  its own connection.
- Substack-style feeds include the full post; items whose feed text is over 500 chars
  skip the scrape step.
- The backup snapshot inherits WAL mode from the live DB; it is switched to
  `journal_mode=DELETE` so a restore is a single file copy.
- `messages.parse()` responses carry Pydantic generics that make `model_dump()` print a
  wall of serialization warnings; `llm.py` dumps them with `warnings=False` before handing
  them to `llm_contact.check()`.
- Chat: the user's message is stored before the model is called, so a failed or stopped reply
  (409 when the model contacts Eli, 502 for a truncated or wordless reply) leaves it saved with
  no answer. The page used to put the text back in the box as well, and the next Send stored it
  twice (rows 29/30 in August). Now it reloads the conversation, restores the draft only if the
  message did not arrive, and shows "Ask for a reply", which posts `message: null` to answer
  the stored message.
- Chat replies stored between 2026-07-27 and 2026-08-05 contain garbled text ("HereHere'the
  heuristic", "would would", and one reply that is only ","). The raw API responses were not
  kept, so the cause is unknown; the stored text is what came back in the `reply` field of the
  structured output. A reply with no word characters is now rejected instead of stored. The old
  rows are still in `conversation_messages` and are sent to the model as history on every
  turn; on 2026-11-12 Opus saw them and contacted Eli about it, which stopped that turn.
- The chat history sent to the model is filtered (`interview._history`): a user message stored
  twice in a row is sent once, and an agent reply with no words is skipped. The rows stay in the
  table and still show in the UI. The interview prompt also tells the model that the garbled
  July/August replies are known. Without both, Opus used `contact_eli` to report the junk on
  three turns in a row on 2026-11-12, and each one stopped the turn (and one pipeline run).
- Accepting a proposal chip does not add an instruction whose exact text is already active.
  Six exact duplicates from July (ids 14-19) were set to `archived` on 2026-11-12.
- Scheduled runs that fire on wake can start before Wi-Fi is up: the run finishes in two
  seconds with "ranking: Connection error." and the feed keeps its old order (runs 280, 284-286).
  The pipeline waits for `api.anthropic.com:443` before the fetch stage (stage "waiting for
  network") and again before each LLM stage. The wait is counted in checks, not clock time: the
  first version allowed 180 seconds by the clock, which keeps running while the Mac sleeps, so
  a run that started in a short network-less wake went ahead offline the moment the Mac next
  woke (runs 297, 300, 301, 314). After 20 minutes awake with no network the run ends as
  `error` with nothing fetched; the next scheduled run tries again.
- Saved links were being lost in two ways, both fixed 2026-11-20. Auto-dismiss (triage score 3
  or less and older than 30 days) applied to them: 52 were dismissed in one sweep on 2026-09-27,
  most of them links whose page could not be fetched, which triage scores near 0 from the title
  alone. And the feed's tail of unranked saved links only listed states `new` and `triaged`, so
  a saved link that had been ranked once (`shown`) and then fell out of the top 75, or that was
  opened but not rated, was in no list at all (29 such links). The 52 are still `dismissed`;
  they are the rows with `found_by='user' AND state_changed_at LIKE '2026-09-27 04:31%'`.
- A network failure while fetching an article's text used to store `''`, which is permanent:
  the item is triaged from its title and never fetched again. Connection errors and timeouts
  now leave the text unset so the next run retries, for two days. An HTTP error (403, 404) or
  an empty extraction still stores `''`.
- feedparser's own downloader has no timeout. Feeds are downloaded with httpx (30s) and the
  bytes handed to feedparser; checked 2026-11-20 against all nine RSS sources, same entries.
- A run that is killed (server restart, reboot) leaves its row `running`. The UI then showed
  "running" with Refresh disabled for up to an hour. Every live run holds `pipeline.lock`, so
  the server now closes any `running` row older than a minute when the lock is free.
- `generate_text` (triage, profile) did not check for a reply cut off at `max_tokens`; a
  truncated taste profile would have been stored and used. It raises now, like the structured calls.
- Sources 10 and 11 are the same blog (URLs differing by a trailing slash) and 3 and 12 are
  both METR (page scan and RSS). Items are deduplicated by URL so nothing shows twice, but each
  is fetched twice per run. Adding a source now refuses a URL or feed that is already there;
  the existing duplicates were left for Eli to pause.
- Ranking output (thinking + 75 rationales) sits close to its token budget; at 16k run 288 was
  cut off mid-JSON, which shows up as a pydantic "Invalid JSON: EOF" error, not the
  `max_tokens` message. The budget is 21,000; the SDK refuses non-streaming calls above
  21,333, so going higher means switching that call to streaming or ranking fewer candidates.
- Ranking only sees the 75 candidates with the highest triage score, so most saved links are
  never ranked. The feed used to put every unranked saved link first; by 2026-11-12 that was 90
  links above the ranked list. Now no saved link goes above the ranked list: unranked saves
  follow it, newest-since-the-last-run first, then by triage score. The ranking prompt
  no longer tells Opus to put saved links at or near the top.
- Python 3.9 compatibility note in `schemas.py` (`Optional[...]`) is historical; the venv
  is Python 3.12 and the rest of the code uses `X | None`.
